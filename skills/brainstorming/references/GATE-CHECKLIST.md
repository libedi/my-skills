# 게이트 체크리스트

이 문서가 스펙 작성 준비도 기준의 **유일한 정의**다. SKILL.md의 진행 판단과 게이트 출력은 이 표를 참조하며, 기준을 따로 적지 않는다.

## 스펙 작성 준비도 판정 기준

Must 항목은 에이전트의 판단만으로 "충족"이 되지 않는다. 증거 기준을 만족하는 내용이 작업 노트에 있어야 충족이다.

| 범주 | Must (필수) | Must 증거 기준 | Nice-to-have (권장) |
|------|-------------|----------------|---------------------|
| 문제 정의 | What + Why 명확 | 사용자가 확인한 한두 문장의 문제 진술 | 대안 배제 이유 |
| 영향 범위 | 대상 모듈 확정 | 모듈명 + 진입점(Job/Step, API, 클래스 등) | In/Out Scope 명시 |
| 데이터 소스 | 주요 테이블/API 식별 | 코드·DDL·문서에서 존재를 확인한 이름 (`[코드에서 확인]`) | 정확한 컬럼 매핑 |
| As-Is 참조 | 전환 대상 식별 (해당 시) | 대상 소스 경로, 또는 사용자가 확인한 "해당 없음" | As-Is 상세 로직 |
| 제약조건 | 알려진 기술 제약 | 출처 태그가 붙은 제약, 또는 사용자가 확인한 "없음" | 비기능 요구사항 |
| 도메인 규칙 | 핵심 비즈니스 규칙 | `[사용자 확정]` 태그가 붙은 규칙 1개 이상 | 엣지 케이스 |
| 요구사항·AC | 착수 대상의 요구사항·비목표 확정, 요구사항마다 핵심 AC 확정, 동작("무엇")에 관한 미결정 없음 | 사용자가 확인한 요구사항 목록과 비목표, 요구사항마다 `[사용자 확정]` 또는 `[추천 수용]` 태그가 붙은 핵심 AC 1개 이상, 예산 이내 ([AC-REFINEMENT](AC-REFINEMENT.md)) | 요구사항별 결정된 예시, 테스트 후보 |
| 스코프 | 단일 스펙에 적합한 크기, 착수 대상 1개 확정 | § 스코프 판정 결과 | 분리 항목의 순서·의존·공유 결정 정리 |

## 스코프 판정

게이트에서 아래를 확정한다. 하나라도 걸리면 분리하고, **이번에 착수할 하나**와 **나머지**를 구분한다.

- **YAGNI**: 지금 시점에서 꼭 필요한가? → 아니면 후속 항목으로 분리.
- **응집도**: 성격이 다른 요건이 한 덩어리로 섞여 있지 않은가? → 섞였으면 관심사별 분리.
- **목적 정합**: 이번 논의의 목적을 벗어난 항목이 있는가? → 있으면 포함/제외 결정. 제외 시 독립 백로그 항목으로.
- **크기**: 목적엔 맞지만 결과 스펙을 집중해서 10분 안에 검토할 수 없을 만큼 큰가? → 크면 단계로 분리. 정제를 마쳤다면 요구사항 수와 핵심 AC 총수를 근거로 판단한다. 요구사항 하나라도 핵심 AC 예산을 넘으면 크기 신호다.

분리 결과:
- **착수 대상 1개**(보통 첫 단계) → 게이트 통과 후 선택지(스펙 작성 / 백로그 등록 / 보류·폐기)로 진행.
- **나머지**(후속 단계·목적 이탈 항목) → § 분리 항목 처리에 따라 백로그에 별도 항목으로 등록.

## 분리 항목 처리

### 공유 결정(이음새) 추출

스펙을 나누면 경계에서 결합 결정이 사라지기 쉽다. 예를 들어 1단계가 만드는 테이블 컬럼을 2단계가 전제로 삼는 경우다. 순서만 기록하면 이 계약이 어느 스펙에도 남지 않는다.

분리가 결정되면:
- 둘 이상의 항목이 공유하는 결정을 작업 노트의 "공유 결정"에 모은다.
- 착수 항목과 관련된 공유 결정은 착수 항목의 스펙 요청에 포함한다. 착수 항목이 그 계약을 먼저 확정하는 쪽이다.
- 후속 항목끼리만 공유하는 결정은 관련된 백로그 항목 모두에 동일하게 기록한다.

### 순차 의존과 백로그 등록

- 분리된 나머지 항목은 각 단계를 **별도 백로그 항목**으로 만든다(하나의 항목 안 체크리스트로 관리하지 않는다). 각 항목은 backlog skill로 등록한다.
- 후속 단계가 선행 단계에 의존하면 그 **선행 의존을 기록**한다(선행 항목 번호, 복수 가능). 선행이 없는 항목(첫 단계·독립 항목)은 선행을 비운다 → 바로 착수 가능.
- 선행 의존의 **표현 형식**(어느 필드/컬럼에 어떻게 적는지)은 `backlog-guide` steering이 정본이다. 이 skill은 "무슨 의존이 있는지"(어느 항목이 어느 항목을 선행으로 갖는지)만 정하고, 형식은 backlog skill/steering에 위임한다. today skill이 이 선행 정보를 조회 계약으로 읽어 착수 가능/대기를 표시한다.
- 항목 본문(배경/목표 등)에 무슨 내용을 담을지는 이 skill이 정하고, 항목 구조·번호·상태 전이·파일 배치는 `backlog-guide`를 따른다.

## 게이트 출력 형식

```
스펙 작성 준비도:
✅ 문제 정의
✅ 영향 범위
✅ 데이터 소스
✅ As-Is 참조: [대상 / 해당 없음]
✅ 제약조건
✅ 도메인 규칙
✅ 요구사항·AC: [요구사항 N개, 핵심 AC M개]
✅ 스코프: [단일 스펙 적합 / N개로 분리 — 착수: X, 나머지 백로그]
❓ [Must 미달 항목]: 이것만 확인하면 됩니다 — [구체적 질문]
💡 [Nice-to-have 미달 항목]: 지금 진행해도 되고, 보강하면 스펙이 더 단단해집니다 — [이유]
→ [판정 결과]
```

판정 결과 뒤에는 아직 더 이야기해도 된다는 것을 한 줄로 덧붙인다.

## 프롬프트 생성 형식

"스펙 작성"에서 현재 세션으로 진입할 수 없거나 "백로그 등록"을 선택한 경우, 아래 형식으로 코드블록을 생성한다. 사용자는 이를 새 세션에 붙여넣는다.

프롬프트는 대화 기억이 아니라 **작업 노트에서** 생성한다. 새 세션은 브레인스토밍 대화를 모르므로, 이 프롬프트가 유일한 맥락이다. 템플릿에서 빠진 정보는 전달되지 않는다.

"백로그 등록"과 분리된 나머지 항목에는 AC를 정제하지 않았으므로, "requirements.md 작성 규칙" 블록을 빼고 요구사항은 이름과 서사까지만 담는다.

```markdown
## 스펙 작성 요청

아래 맥락을 기반으로 스펙을 작성해줘. `[코드에서 추정]` 항목은 스펙 작성 전에 먼저 검증해줘.

requirements.md 작성 규칙:
- 아래 "요구사항과 핵심 AC"의 AC만 1:1로 옮기고, 새 AC를 만들지 마.
- 꼭 필요해 보이는 AC가 있으면 requirements.md 끝의 "추가 후보" 섹션에만 적어줘. 내가 채택한 것만 본문으로 올린다.
- 테스트 후보는 requirements.md에 올리지 말고 tasks.md의 테스트 작업으로 반영해줘.
- MODULE_SPEC 반영 후보는 AC로 쓰지 말고 따로 알려줘.
- requirements.md 작성 후, 핵심 AC 개수가 아래 목록과 같은지 한 줄로 보고해줘.

**기능**: [기능명]
**모듈**: [대상 모듈명]
**배경**: [왜 필요한지]
**목표**: [무엇을 달성하려 하는지]
**데이터 소스**: [주요 테이블/API]
**제약사항**:
- [제약] [출처 태그]
**결정사항**:
- [브레인스토밍 중 내린 결정] [출처 태그]
**비목표**:
- [이번에 하지 않는 것]
**요구사항과 핵심 AC**:
- R1. [요구사항 이름] — [한두 문장 서사]
  - AC-1.1 [문장] [출처 태그]
  - 결정된 예시: [표 또는 요약]
**테스트 후보** (requirements.md에 올리지 않음):
- R1: [항목]
**MODULE_SPEC 반영 후보**:
- [항목]
**기각된 대안**:
- [대안] — [기각 이유]
**공유 결정** (분리된 경우):
- [다른 항목과 공유하는 결정]
**참조**: [As-Is 소스, 관련 문서 경로 등]
**미결정** (스펙 작성 중 설계 판단 필요):
- [항목]
**확인 필요** (사실 확인):
- [항목] — [확인할 곳/사람]
```
