# 브레인스토밍

아직 스펙이 작성되지 않은 **새 기능**의 사전 논의에 적용한다.

이미 스펙(요구사항·설계 문서)이 있는 기능의 수정/보완은 이 skill을 따르지 않고, 해당 기능의 스펙 워크플로우에서 기존 스펙을 갱신한다. 새 기능인지 기존 기능의 확장인지 애매하면 관련 스펙 파일이 있는지 먼저 확인하고, 어느 쪽으로 진행할지 사용자에게 한 번 묻는다.

## 목적

스펙 문서의 품질은 사전 정보 수집의 깊이에 비례한다. 이 단계에서 사용자와 에이전트의 인식을 동기화하여, 충분하지 않은 정보로 스펙을 추측해서 작성하는 것을 방지한다.

## 연동

이 skill은 특정 런타임이나 스펙 도구를 전제하지 않는다. 아래 연동 대상은 프로젝트에 있으면 쓰고, 없으면 대체 경로를 따른다.

| 연동 대상 | 뜻 | 예 | 없을 때 |
|---|---|---|---|
| 스펙 도구 | 요구사항·설계·작업 문서를 만드는 도구나 워크플로우 | Kiro specs, Spec Kit, OpenSpec | 게이트 뒤에 붙여넣기용 스펙 작성 요청을 만든다 |
| 백로그 | 시기가 미정인 항목과 분리된 후속 항목을 등록하는 곳 | 프로젝트의 backlog skill, 이슈 트래커 | 항목 내용을 코드블록으로 만들어 사용자가 원하는 곳에 등록하게 한다 |
| 모듈 문서 | 기능 하나가 아니라 모듈 전체에 적용되는 규칙을 담은 문서 | MODULE_SPEC, 아키텍처 결정 기록 | 반영 후보를 사용자에게 제시만 한다 |
| research skill | 여러 대안을 독립적으로 탐색하는 skill | 이 저장소의 research skill | 이 자리에서 직접 추천안과 대안을 낸다 |
| 보드 | 질문을 브라우저 화면으로 보여주고 답을 받는 표시 방식. 진행 판단에는 관여하지 않는다 | [보드](references/BOARD.md) (Node 18 이상) | 프롬프트로 진행한다 |

이 skill에서 "요구사항 문서", "설계 문서", "작업 문서"는 스펙 도구가 만드는 해당 문서를 뜻한다. 예를 들어 Kiro specs에서는 각각 `requirements.md`, `design.md`, `tasks.md`다.

## 즉시 실행

이 skill이 활성화되면, 에이전트는 **즉시** 다음을 수행한다:

1. `.brainstorm/`에 기존 작업 노트가 있는지 확인한다. 있으면 각 노트의 주제와 마지막 논의 지점을 보여주고, 이어서 할지 새로 시작할지 묻는다(§ 작업 노트).
2. 새로 시작하면 사용자의 첫 메시지를 질문 축에 대입하여, 이미 충족된 축과 미달 축을 분류한다.
3. 미달 축 중 가장 핵심적인 1개에 대해 열린 질문을 던진다.
4. 사용자가 첫 메시지에서 이미 구체적 맥락(대상 모듈, 목표, 제약)을 제시한 경우, 해당 정보를 질문 축에 대입한 후 **미달 축에 대해서만** 질문한다. 이미 충족된 축을 다시 묻지 않는다.

코드 탐색·문서 확인 등 자동 수집 가능한 정보는 질문 전에 먼저 수행하되, 수집 결과를 공유한 후 미달 축에 대해 질문하는 흐름을 유지한다.

## 작업 노트

대화 상태는 에이전트의 기억이 아니라 **작업 노트 파일**에 둔다. 긴 대화에서 컨텍스트가 압축되거나, 사용자가 중간에 이탈했다가 돌아와도 논의가 이어지게 하기 위함이다.

- **위치**: `.brainstorm/<주제-슬러그>-<4자리 해시>.md`. 여러 브레인스토밍이 동시에 진행될 수 있으므로, 주제 슬러그로 찾을 수 있게 하고 해시로 이름 충돌을 피한다.
- **형식**: [작업 노트 템플릿](assets/brainstorm-note.md)을 따른다. 대화 원문은 담지 않고 결론과 남은 질문만 담는다.
- **gitignore**: 처음 노트를 만들 때 `.gitignore`에 `.brainstorm/`이 없으면 추가하고, 한 줄로 알린다.
- **갱신**: 축 현황, 결정사항, 기각된 대안, 미결정·확인 필요 항목, 마지막 논의 지점이 바뀔 때마다 갱신한다.
- **출처 태그**: 결정사항과 제약에는 출처를 붙인다.
  - `[사용자 확정]` 사용자가 직접 정한 것
  - `[추천 수용]` 에이전트 추천을 사용자가 받아들인 것
  - `[코드에서 확인]` 코드·DDL·문서에서 직접 확인한 사실
  - `[코드에서 추정]` 코드를 보고 에이전트가 추론한 것 (스펙 단계에서 검증 필요)
  - `[가정]` 근거가 부족한 채 진행하려고 잠정적으로 정한 것 (확인할 곳이나 사람을 "확인 필요"에 함께 적는다)
- **참조**: 사용자가 제시한 파일과 탐색한 코드는 내용이 아니라 경로만 기록하고, 필요할 때 다시 읽는다.
- **이어하기**: 노트를 읽은 뒤 바로 다음 질문으로 가지 않는다. 정리된 내용을 짧게 요약해 보여주고 맞는지 확인받는다. 노트에는 대화의 뉘앙스가 담기지 않으므로, 사용자가 보충하면 노트에 반영하고 탐색으로 돌아간다.
- **삭제**: § 마무리에서 사용자가 종료를 확인하면 노트를 삭제한다. 파일은 내부 구현이므로 삭제 여부를 따로 묻지 않는다.
- **오래된 노트**: 활성화 시 마지막 갱신 후 14일이 지난 노트가 있으면 정리할지 함께 묻는다. 대화 중간에 이탈한 세션은 마무리 질문에 도달하지 못하므로, 이 단계가 고아 노트를 정리하는 유일한 경로다.

## 진행 판단

에이전트는 탐색 → 정리 → 정제 → 게이트의 네 단계를 내부적으로 구분하되, **사용자에게 단계 이름이나 번호를 알리지 않는다**. 사용자가 단계를 의식하면 논의를 절차로 받아들여 "더 진행하면 안 되나?", "새 생각이 났는데 돌아갈 수 없나?" 같은 압박을 느낀다.

단계는 노트에 저장하지 않고, 매번 노트의 축 현황과 사용자 확인 여부에서 도출한다. 충족 여부의 기준은 [게이트 체크리스트](references/GATE-CHECKLIST.md)가 유일한 정의다.

- **탐색 → 정리**: 체크리스트의 Must 중 문제 정의와 영향 범위가 노트에서 충족일 때
- **정리 → 정제**: 영역별 요약을 제시하고 사용자가 확인(또는 추가 정보 없이 동의)했고, 설계 방향이 정해졌을 때(선택지가 없으면 바로)
- **정제 → 게이트**: 착수 대상의 모든 요구사항에 핵심 AC가 정해졌을 때
- **정리·정제 → 탐색**: 사용자가 새로운 정보를 제공하여 기존 이해가 수정될 때
- **정제 → 정리**: 핵심 AC 예산을 넘거나 요구사항이 너무 많아 스코프를 다시 논의해야 할 때
- **어느 단계 → 논의 종료**: 사용자가 그만하기를 원하거나 § 논의 종료의 제안 신호가 보일 때. 게이트를 거치지 않는다.

## 워크플로우

### 탐색 (인터뷰)

사용자의 아이디어를 듣고, 빠진 맥락을 수집한다.

**원칙:**
- 첫 질문은 항상 1개 — 핵심 컨텍스트를 파악하는 열린 질문
- 후속 질문은 최대 2-3개를 한 번에 묶어서 던진다. 이는 한 번에 묻는 양에 대한 가이드일 뿐이다. 수렴 시점은 질문 횟수가 아니라 축 현황과 사용자 신호로 판단한다. 사용자가 아직 발산 중이면 게이트로 끌고 가지 않는다.
- **참조 자료 수집**: 사용자가 갖고 있는 관련 문서, 분석 결과, 파일 등을 초기에 물어본다
  - "이 기능과 관련해서 참조해야 할 문서나 파일이 있나요?"
  - 사용자가 제시한 파일은 반드시 읽고 내용을 반영한다
- 자동 수집 가능한 정보는 물어보지 않는다:
  - 코드 탐색, DB 스키마, As-Is 분석 결과 등은 에이전트가 직접 확인
  - "이런 맥락 맞죠?"로 확인만 받는다
  - 직접 확인한 사실과 추론한 내용은 출처 태그로 구분해 노트에 기록한다
- 답변에서 새로운 질문이 파생되면 추가로 물어본다

**관점 카드 (문제 진술이 막연할 때):**

첫 열린 질문에 대한 답이 여러 방향으로 읽히거나, 사용자가 무엇이 문제인지 스스로 말하기 어려워할 때 쓴다. 사람은 "무엇이 문제인가"를 백지에서 말하기는 어려워도, 제시된 관점에 "이건 아니다"라고는 바로 반응할 수 있다.

- **자기 말 먼저**: 사용자가 자기 말로 한 번 답한 뒤에 낸다. 보기를 먼저 보여주면 에이전트의 틀이 그대로 사용자의 틀이 된다.
- **서로 부딪히는 관점**: 같은 생각의 변형이 아니라 문제의 원인이나 방향이 서로 다른 관점 3~4개를 한두 문장씩 제시한다.
- **고르지 않고 반응한다**: 관점마다 끌림 / 일부 / 아님으로 답하게 한다. 번호 목록으로 제시하고 "1 끌림, 3 아님"처럼 짧게 답해도 된다고 알린다. 아님 반응도 끌림만큼 중요한 신호다. "어느 것도 아님"과 사용자의 새 관점은 언제나 받는다.
- **좁히기 위한 도구다**: 탐색 중 한두 번만 쓰고, 결과는 사용자가 확인한 문제 정의 한 문장으로 모은다. 아님으로 답한 관점은 다시 꺼내지 않는다.

**질문 축:**

| 축 | 탐색 내용 |
|----|-----------|
| 문제 정의 | 왜 이것이 필요한가? 현재 무엇이 부족한가? |
| 영향 범위 | 어떤 모듈에 속하는 작업인가? 다른 모듈에 영향이 있는가? |
| 데이터 소스 | 어떤 테이블/API/시스템에서 데이터를 가져오는가? |
| As-Is 참조 | 전환 대상인 기존 시스템 로직이 있는가? |
| 도메인 규칙 | 핵심 비즈니스 규칙은 무엇인가? 엣지 케이스는? |
| 제약조건 | 알려진 기술적/시간적 제약이 있는가? |

### 정리 (피드백)

수집된 정보를 요약하고, 빠진 부분을 보완한다. **영역별로 나눠서** 확인을 받는다.

**수행 내용:**
1. 지금까지 수집된 정보를 영역별로 구조화하여 제시한다:
   - 문제 정의 & 목표
   - 영향 범위 & 데이터 소스
   - 기술적 제약 & 설계 방향
   - 정보가 충분히 복잡한 경우: 영역별로 나눠 순차적으로 확인받는다
   - 간단한 경우: 한 번에 요약하고 확인받아도 된다
2. 발견된 기술적 제약사항을 선제 고지한다
3. **설계 방향 제시**: 설계 선택지가 존재하면 기본 추천안을 먼저 제시하고, 대안은 트레이드오프와 함께 간략히 언급한다
   - 추천 옵션: 핵심 아이디어, 장점, 추천 이유를 명확히
   - 대안: "X 방식도 가능하지만, Y 때문에 추천안이 더 적합" 형태로 간결하게
   - 대안이 존재하지 않는 경우(유일한 방법)에만 1개로 갈 수 있다
   - 사용자가 대안을 기각하면 기각 이유와 함께 노트의 "기각된 대안"에 기록한다
   - **복잡한 설계 선택지일 때 research 옵션**: 여러 접근이 실제로 경합하거나 단일 관점 앵커링이 우려되어 에이전트 혼자 대안을 내기 부족하다고 판단되면, research skill이 설치되어 있으면 그것으로 대안을 탐색하는 것을 **선택지로 제시**한다. 기본은 이 자리에서 직접 추천안을 내는 것이고, research는 예외다 — 브레인스토밍은 가벼운 대화이고 research는 수십 분이 걸리므로 대부분은 research 없이 진행한다. research 활성화 시의 비용 고지·승인은 research skill이 소유한 활성화 승인 게이트가 담당하므로 여기서 재기술하지 않는다.
4. **스코프 건전성 검증**: 범위가 비대해지거나 성격이 다른 요건이 뒤섞이지 않도록 적극적으로 확인한다.
   - "이 부분은 현재 시점에서 꼭 필요한가요? 후속 스펙으로 분리할 수 있을까요?"
   - 판정 기준(YAGNI, 응집도, 목적 정합, 크기)은 [게이트 체크리스트](references/GATE-CHECKLIST.md) § 스코프 판정을 따른다
   - 분리 신호가 감지되면 사용자와 분리 여부를 논의한다. 최종 판정은 게이트에서 확정한다.
5. 모호함을 명시적으로 분리하여 노트에 기록한다:
   - **미결정**: 설계("어떻게") 판단이 필요한 것 (스펙 작성 중 결정). 동작("무엇")에 관한 모호함은 미결정으로 넘기지 않고 정제 단계에서 해소한다.
   - **확인 필요**: 사실 확인이 필요한 것 (확인할 곳이나 사람을 함께 적는다)

**단계 간 순환 허용:**
- 요약을 보고 사용자가 추가 정보를 제공하면 탐색으로 돌아간다
- 엄격한 순서가 아닌 자연스러운 순환을 허용한다

### 정제 (요구사항·AC)

착수 대상의 요구사항과 핵심 AC를 사용자와 함께 정한다. 스펙 도구가 먼저 생성하고 나중에 리뷰하는 구조라면, 여기서 동작에 관한 결정이 비어 있으면 스펙 도구가 그 자리를 추측한 AC로 채운다. 이 단계는 그 빈자리를 사람의 결정으로 먼저 채우는 자리다.

정제에 들어가면 [요구사항·AC 정제](references/AC-REFINEMENT.md)를 읽어 진행 순서, 분류 기준, 예산, 노트 기록 형식, 스펙 인계 규칙을 참조한다.

**흐름 요약:**
1. 요구사항 목록과 비목표를 제시하고 확인받는다.
2. 요구사항마다 AC 목록 대신 **결정 질문**을 던진다. 추천 답과 예시 표 초안을 함께 보여준다.
3. 답에서 핵심 AC를 도출하고, 나머지 후보는 테스트 후보·횡단 관심사·구현 세부로 나눠서 보여준다. 사용자는 분류만 조정한다.
4. 요구사항당 핵심 AC가 예산을 넘으면 멈추고 분할 또는 스코프 분리를 논의한다.

스코프 분리가 이미 정해졌다면 착수 대상만 정제한다. 나머지 항목은 요구사항 목록까지만 기록한다.

### 게이트 (확인)

스펙 작성 준비도를 체크리스트로 판단한다.

게이트에 도달하면 [게이트 체크리스트](references/GATE-CHECKLIST.md)를 읽어 판정 기준, 출력 형식, 프롬프트 생성 형식을 참조한다.

**판정:**
- Must 항목이 모두 충족 → 스펙 작성 진입 가능
- Must 항목 미달 → 해당 항목만 짧게 추가 수집한다 (탐색으로 돌아감). 같은 Must가 되물어도 채워지지 않으면 § 논의 종료의 제안 신호다.
- Nice-to-have 미달 → 스펙 작성 중 보완 가능 (진입 허용)

**표현:** 미달 항목을 "불합격"처럼 보이게 하지 않는다. "이것만 확인하면 됩니다", "지금 진행해도 되고, 이것까지 보면 스펙이 더 단단해집니다"처럼 무엇을 하면 되는지와 선택권을 함께 보여주고, 아직 더 이야기해도 된다는 것을 알린다.

**게이트 통과 후 행동:**

게이트에서 스코프 분리가 필요하다고 판정된 경우, 먼저 **이번에 착수할 하나**(보통 첫 단계)와 **나머지(후속 단계 / 이번 목적 밖 항목)**를 구분한다.

- **이번에 착수할 하나**만 아래 선택지로 진행한다.
- **나머지 항목**은 백로그에 등록한다(§ 연동). 공유 결정 추출과 순차 의존 기록은 [게이트 체크리스트](references/GATE-CHECKLIST.md) § 분리 항목 처리를 따른다.

분리가 필요 없으면(스코프 건전) 곧바로 아래 선택지로 진행한다.

사용자에게 다음 선택지를 제시한다:

1. **"스펙 작성"** — 현재 세션에서 스펙 도구의 워크플로우에 진입할 수 있으면 바로 진행한다. 스펙 도구가 기능·버그 수정 같은 유형 선택을 요구하면 그 단계부터 시작한다. 세션 제약 등으로 진입할 수 없거나 스펙 도구가 없으면, 작업 노트에서 붙여넣기용 프롬프트를 생성하고 스펙을 작성할 새 세션에서 사용하도록 안내한다. 어느 경로든 [요구사항·AC 정제](references/AC-REFINEMENT.md) § 스펙 인계 규칙을 따른다.
2. **"백로그 등록"** — 시기가 미정인 경우. § 논의 종료를 따른다.
3. **"보류·폐기"** — 지금 만들지 않는 것이 맞다고 판단된 경우. § 논의 종료를 따른다.

2와 3은 게이트를 통과해야만 고를 수 있는 선택지가 아니다. 게이트는 스펙 작성의 전제조건이다.

### 논의 종료

게이트의 체크리스트는 **스펙 작성** 준비도다. 미루거나 만들지 않기로 정하는 데에는 스펙 작성 준비도가 필요 없으므로, 아래 두 출구는 어느 단계에서든 고를 수 있다.

- **백로그 등록** — 시기가 미정인 경우. 사용자가 확인한 문제 정의만 있으면 된다. 프롬프트 생성 형식과 같은 내용으로 백로그에 항목을 추가한다. 백로그 도구가 있으면 등록 경로와 형식은 그 도구의 규칙을 따르고, 없으면 항목 내용을 코드블록으로 만들어 준다(§ 연동). 정제하지 않은 요구사항은 이름과 서사까지만 담고, 착수할 때 다시 브레인스토밍한다.
- **보류·폐기** — 논의 결과 지금 만들지 않는 것이 맞다고 판단된 경우. 따로 필요한 조건은 없다. 사유를 사용자와 한두 문장으로 정리하고, 남길 곳(백로그 등)이 있으면 기록한다.

**제안 시점:** 출구를 매번 선택지로 보여주지 않는다. 언제든 나갈 수 있다는 것을 메뉴처럼 반복하면 논의를 빨리 끝내라는 압박으로 읽힌다(단계를 알리지 않는 것과 같은 이유). 아래 신호가 보일 때만 제안한다.

- 사용자가 필요성이나 가치에 회의적인 말을 할 때
- 기능을 전제로 한 Must(영향 범위, 데이터 소스)가 되물어도 계속 채워지지 않을 때 — 아직 기능으로 정할 단계가 아닌 주제일 수 있다

사용자가 먼저 그만하기를 원하면 신호와 상관없이 바로 처리한다. 처리를 마치면 § 마무리로 간다.

### 마무리

선택지(게이트 통과 후 선택지 또는 § 논의 종료) 처리를 마친 뒤 "브레인스토밍을 마무리할까요, 더 이야기할 게 있나요?"라고 묻는다.

- **마무리**: 작업 노트를 삭제한다.
- **더 이야기**: 탐색으로 돌아간다. 새 생각을 꺼낼 마지막 기회로 자연스럽게 활용한다.

현재 세션에서 스펙 작성에 바로 진입한 경우, 노트가 스펙 작성의 입력이므로 마무리 질문은 요구사항 문서가 생성된 뒤에 한다.

## 에이전트 행동 규칙

- 이 워크플로우 중에는 스펙 문서(요구사항·설계·작업 문서)를 생성하지 않는다. 작업 노트는 스펙 문서가 아니다.
- 사용자의 아이디어에 무조건 동의하지 않는다. 기술적으로 더 나은 방향이 있다면 근거와 함께 제안한다.
- 정제 중에는 AC 목록을 먼저 제시하고 승인받는 방식을 쓰지 않는다. 결정 질문이 먼저이고, AC는 그 답에서 도출한다.
- 질문 시 코드/DB/문서를 직접 확인할 수 있는 것은 먼저 확인하고 결과를 공유한다.
- 진행 단계를 사용자에게 명시적으로 알리지 않는다(자연스러운 대화 흐름 유지). 진행 판단은 작업 노트에서 도출한다.
- 게이트 확인 시에만 체크리스트 형태로 현황을 보여준다.
