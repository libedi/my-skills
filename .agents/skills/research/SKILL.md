# Research

Use this skill for research, not as authorization to edit source material, publish, contact others, or change an external system. The [integrated design](../../../docs/research-harness-design/research-harness-design.md) explains the rationale. The references below are the execution contract.

## Host Agent

1. Preserve the user's original request verbatim. Make an Intake Packet with confirmed user decisions, hard constraints, source locations, available tools, and limits. Label earlier facts, user statements, and assumptions separately. Exclude tentative solutions, agent recommendations, and the whole prior conversation.
2. Confirm that a fresh-context subagent can start and that custom agent `research_orchestrator` is loaded with its configured model and reasoning effort. The v1 profile is `gpt-6-astra` at `high`. Use `fork_turns="none"` or an equivalent fresh start. A TOML file's presence does not prove that the running agent has those settings or isolated context. If either requirement cannot be verified, do not claim to run the Harness or silently substitute a weaker model. Explain the capability gap and resolve the execution path with the user.
3. Start one Research Orchestrator for the request. Pass only the Intake Packet and the location and version of this skill and its relevant references. Do not assume the Host's loaded skill text is inherited. Keep user decisions, permission boundaries, and final delivery with the Host.
4. Compare the first plan with the original request for missing critical questions or outcomes, changed hard constraints, unwarranted scope, and duplicated axes. Return specific gaps without prescribing a preferred answer. Preserve the first plan and revision reason.
5. Compare the final report and validation record with the original request. Deliver the result with material evidence, unresolved questions, status, and limitations. Send substantive corrections back to the Orchestrator for reconciliation; do not quietly rewrite findings.

A short self-contained fact lookup does not need the Harness. A substantive research request without a fresh Orchestrator is a capability failure, not an independent multi-agent study.

## Research Orchestrator

Read [agent contracts](references/agent-contracts.md), [axis design](references/axis-design.md), and [evidence and evaluation](references/evidence-and-evaluation.md). Read [complex requests](references/complex-requests.md) when the request has distinct subproblems or dependent deliverables. Use [JSON contracts](references/json-contracts.md) for machine-readable records and the validator. Start from the [Brief template](assets/research-brief.json) and [report template](assets/research-report.md) where helpful. Run `scripts/validate.py` from this skill directory, or call it by its full path from another working directory.

1. Classify purpose, hard constraints, preferences, hypotheses, and required outcomes. Build a Brief from the Intake Packet without promoting a hypothesis or recommendation to fact. For complex requests map every parent question and required outcome to a Subproblem; keep one Orchestrator and execute Research Units sequentially.
2. Design up to three initial axes per Unit. Give each an actual question and evidence strategy, and assign every required question a primary axis. Use one axis when splitting adds no value. Preserve the first plan for the Host's original-request review. Run `scripts/validate.py plan --state <state.json>` before dispatch when file-based checks are available. A structural pass does not establish axis quality.
3. Own one ledger. Reserve and validate each task before dispatch with `scripts/validate.py dispatch --ledger <ledger.json> --unit <unit-id>`. Round 1 allows at most 3 initial tasks. Round 2 allows at most 2 supplementary tasks, including at most 1 Extra Explorer, 1 Critic, and 1 retry. Total investigation tasks are at most 5 per Unit. One existing-evidence-only Status Check per Unit is separate; a complex request may use at most 2 final consistency tasks. Count dispatched failures and cancellations; release only pre-dispatch reservations, with a reason.
4. Delegate one level to Explorer or Critic with only the Unit Brief, assignment, common criteria, source-access limits, and output contract. Initial Explorers do not see one another's findings. Use the `research_explorer` (`gpt-6-sol`, `medium`) and `research_critic` (`gpt-6-sol`, `high`) project profiles when they can be selected and their applied settings verified. Otherwise set model and reasoning explicitly for each role and record the actual values; do not accidentally inherit the Orchestrator's costly model. If nested delegation is unavailable, give the Host an exact sibling assignment and receive its unchanged result; keep the ledger and research judgment yourself. At most 3 investigation agents may be active, further limited by slots remaining after the Orchestrator occupies one.
5. Validate collected results with `scripts/validate.py result --state <state.json> --result <result.json>`. Read full results that affect the conclusion; a short pointer is insufficient. Separate facts, inferences, proposals, source independence, counterevidence, and unknowns. Judge whether sources actually support claims; the script cannot. Choose extra investigation, verification, Critic, or synthesis only for a concrete gap within budget.
6. For `complete` require every critical question answered, required outcomes mapped, no unresolved blocking objection, and no stale essential complex result. Otherwise distinguish `partial` from `needs_user_decision` by cause. Consider one independent, read-only Status Check if proposing `complete` without a Critic. Run `scripts/validate.py report --state <state.json> --ledger <ledger.json>` and record any unrun check.
7. Return a decision-ready report plus plan, ledger, and validation summaries to the Host. Include source locations, applicability, counterevidence, unresolved questions, and the actual exit reason. Never claim that unverified context isolation, model settings, deadlines, or semantic judgments were mechanically enforced.

Use `research/<run-id>/state.json`, `ledger.json`, `results/`, and optionally `report.md` when writable and useful. Avoid unnecessary copies of nonpublic material. If safe file storage or Python is unavailable, carry equivalent structured records inline and mark affected checks unrun. Never present an unrun check as passed.
