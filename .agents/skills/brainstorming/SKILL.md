# 브레인스토밍

아직 스펙이 작성되지 않은 **새 기능**의 사전 논의에 적용한다.

이미 스펙(requirements.md, design.md)이 있는 기능의 수정/보완은 이 skill을 따르지 않고, 해당 기능의 스펙 워크플로우에서 기존 스펙을 갱신한다. 새 기능인지 기존 기능의 확장인지 애매하면 관련 스펙 파일이 있는지 먼저 확인하고, 어느 쪽으로 진행할지 사용자에게 한 번 묻는다.

## 목적

스펙 문서의 품질은 사전 정보 수집의 깊이에 비례한다. 이 단계에서 사용자와 에이전트의 인식을 동기화하여, 충분하지 않은 정보로 스펙을 추측해서 작성하는 것을 방지한다.

## 즉시 실행

이 skill이 활성화되면, 에이전트는 **즉시** 다음을 수행한다:

1. `.brainstorm/`에 기존 작업 노트가 있는지 확인한다. 있으면 각 노트의 주제와 마지막 논의 지점을 보여주고, 이어서 할지 새로 시작할지 묻는다(§ 작업 노트).
2. 새로 시작하면 사용자의 첫 메시지를 질문 축에 대입하여, 이미 충족된 축과 미달 축을 분류한다.
3. 미달 축 중 가장 핵심적인 1개에 대해 열린 질문을 던진다.
4. 사용자가 첫 메시지에서 이미 구체적 맥락(대상 모듈, 목표, 제약)을 제시한 경우, 해당 정보를 질문 축에 대입한 후 **미달 축에 대해서만** 질문한다. 이미 충족된 축을 다시 묻지 않는다.

코드 탐색·문서 확인 등 자동 수집 가능한 정보는 질문 전에 먼저 수행하되, 수집 결과를 공유한 후 미달 축에 대해 질문하는 흐름을 유지한다.

## 작업 노트

대화 상태는 에이전트의 기억이 아니라 **작업 노트 파일**에 둔다. 긴 대화에서 컨텍스트가 압축되거나, 사용자가 중간에 이탈했다가 돌아와도 논의가 이어지게 하기 위함이다.

- **위치**: `.brainstorm/<주제-슬러그>-<4자리 해시>.md`. 여러 브레인스토밍이 동시에 진행될 수 있으므로, 주제 슬러그로 찾을 수 있게 하고 해시로 이름 충돌을 피한다.
- **형식**: [작업 노트 템플릿](assets/brainstorm-note.md)을 따른다. 대화 원문은 담지 않고 결론과 남은 질문만 담는다.
- **gitignore**: 처음 노트를 만들 때 `.gitignore`에 `.brainstorm/`이 없으면 추가하고, 한 줄로 알린다.
- **갱신**: 축 현황, 결정사항, 기각된 대안, 미결정·확인 필요 항목, 마지막 논의 지점이 바뀔 때마다 갱신한다.
- **출처 태그**: 결정사항과 제약에는 출처를 붙인다.
  - `[사용자 확정]` 사용자가 직접 정한 것
  - `[추천 수용]` 에이전트 추천을 사용자가 받아들인 것
  - `[코드에서 확인]` 코드·DDL·문서에서 직접 확인한 사실
  - `[코드에서 추정]` 코드를 보고 에이전트가 추론한 것 (스펙 단계에서 검증 필요)
- **참조**: 사용자가 제시한 파일과 탐색한 코드는 내용이 아니라 경로만 기록하고, 필요할 때 다시 읽는다.
- **이어하기**: 노트를 읽은 뒤 바로 다음 질문으로 가지 않는다. 정리된 내용을 짧게 요약해 보여주고 맞는지 확인받는다. 노트에는 대화의 뉘앙스가 담기지 않으므로, 사용자가 보충하면 노트에 반영하고 탐색으로 돌아간다.
- **삭제**: § 마무리에서 사용자가 종료를 확인하면 노트를 삭제한다. 파일은 내부 구현이므로 삭제 여부를 따로 묻지 않는다.
- **오래된 노트**: 활성화 시 마지막 갱신 후 14일이 지난 노트가 있으면 정리할지 함께 묻는다. 대화 중간에 이탈한 세션은 마무리 질문에 도달하지 못하므로, 이 단계가 고아 노트를 정리하는 유일한 경로다.

## 진행 판단

에이전트는 탐색 → 정리 → 게이트의 세 단계를 내부적으로 구분하되, **사용자에게 단계 이름이나 번호를 알리지 않는다**. 사용자가 단계를 의식하면 논의를 절차로 받아들여 "더 진행하면 안 되나?", "새 생각이 났는데 돌아갈 수 없나?" 같은 압박을 느낀다.

단계는 노트에 저장하지 않고, 매번 노트의 축 현황과 사용자 확인 여부에서 도출한다. 충족 여부의 기준은 [게이트 체크리스트](references/GATE-CHECKLIST.md)가 유일한 정의다.

- **탐색 → 정리**: 체크리스트의 Must 중 문제 정의와 영향 범위가 노트에서 충족일 때
- **정리 → 게이트**: 영역별 요약을 제시하고 사용자가 확인(또는 추가 정보 없이 동의)했을 때
- **정리 → 탐색**: 사용자가 새로운 정보를 제공하여 기존 이해가 수정될 때

## 워크플로우

### 탐색 (인터뷰)

사용자의 아이디어를 듣고, 빠진 맥락을 수집한다.

**원칙:**
- 첫 질문은 항상 1개 — 핵심 컨텍스트를 파악하는 열린 질문
- 후속 질문은 최대 2-3개를 한 번에 묶어서 던진다. 이는 한 번에 묻는 양에 대한 가이드일 뿐이다. 수렴 시점은 질문 횟수가 아니라 축 현황과 사용자 신호로 판단한다. 사용자가 아직 발산 중이면 게이트로 끌고 가지 않는다.
- **참조 자료 수집**: 사용자가 갖고 있는 관련 문서, 분석 결과, 파일 등을 초기에 물어본다
  - "이 기능과 관련해서 참조해야 할 문서나 파일이 있나요?"
  - 사용자가 제시한 파일은 반드시 읽고 내용을 반영한다
- 자동 수집 가능한 정보는 물어보지 않는다:
  - 코드 탐색, DB 스키마, As-Is 분석 결과 등은 에이전트가 직접 확인
  - "이런 맥락 맞죠?"로 확인만 받는다
  - 직접 확인한 사실과 추론한 내용은 출처 태그로 구분해 노트에 기록한다
- 답변에서 새로운 질문이 파생되면 추가로 물어본다

**질문 축:**

| 축 | 탐색 내용 |
|----|-----------|
| 문제 정의 | 왜 이것이 필요한가? 현재 무엇이 부족한가? |
| 영향 범위 | 어떤 모듈에 속하는 작업인가? 다른 모듈에 영향이 있는가? |
| 데이터 소스 | 어떤 테이블/API/시스템에서 데이터를 가져오는가? |
| As-Is 참조 | 전환 대상인 기존 시스템 로직이 있는가? |
| 도메인 규칙 | 핵심 비즈니스 규칙은 무엇인가? 엣지 케이스는? |
| 제약조건 | 알려진 기술적/시간적 제약이 있는가? |

### 정리 (피드백)

수집된 정보를 요약하고, 빠진 부분을 보완한다. **영역별로 나눠서** 확인을 받는다.

**수행 내용:**
1. 지금까지 수집된 정보를 영역별로 구조화하여 제시한다:
   - 문제 정의 & 목표
   - 영향 범위 & 데이터 소스
   - 기술적 제약 & 설계 방향
   - 정보가 충분히 복잡한 경우: 영역별로 나눠 순차적으로 확인받는다
   - 간단한 경우: 한 번에 요약하고 확인받아도 된다
2. 발견된 기술적 제약사항을 선제 고지한다
3. **설계 방향 제시**: 설계 선택지가 존재하면 기본 추천안을 먼저 제시하고, 대안은 트레이드오프와 함께 간략히 언급한다
   - 추천 옵션: 핵심 아이디어, 장점, 추천 이유를 명확히
   - 대안: "X 방식도 가능하지만, Y 때문에 추천안이 더 적합" 형태로 간결하게
   - 대안이 존재하지 않는 경우(유일한 방법)에만 1개로 갈 수 있다
   - 사용자가 대안을 기각하면 기각 이유와 함께 노트의 "기각된 대안"에 기록한다
   - **복잡한 설계 선택지일 때 research 옵션**: 여러 접근이 실제로 경합하거나 단일 관점 앵커링이 우려되어 에이전트 혼자 대안을 내기 부족하다고 판단되면, [research skill](../research/SKILL.md)로 대안을 탐색하는 것을 **선택지로 제시**한다. 기본은 이 자리에서 직접 추천안을 내는 것이고, research는 예외다 — 브레인스토밍은 가벼운 대화이고 research는 수십 분이 걸리므로 대부분은 research 없이 진행한다. research 활성화 시의 비용 고지·승인은 research skill이 소유한 활성화 승인 게이트가 담당하므로 여기서 재기술하지 않는다.
4. **스코프 건전성 검증**: 범위가 비대해지거나 성격이 다른 요건이 뒤섞이지 않도록 적극적으로 확인한다.
   - "이 부분은 현재 시점에서 꼭 필요한가요? 후속 스펙으로 분리할 수 있을까요?"
   - 판정 기준(YAGNI, 응집도, 목적 정합, 크기)은 [게이트 체크리스트](references/GATE-CHECKLIST.md) § 스코프 판정을 따른다
   - 분리 신호가 감지되면 사용자와 분리 여부를 논의한다. 최종 판정은 게이트에서 확정한다.
5. 모호함을 명시적으로 분리하여 노트에 기록한다:
   - **미결정**: 설계 판단이 필요한 것 (스펙 작성 중 결정)
   - **확인 필요**: 사실 확인이 필요한 것 (확인할 곳이나 사람을 함께 적는다)

**단계 간 순환 허용:**
- 요약을 보고 사용자가 추가 정보를 제공하면 탐색으로 돌아간다
- 엄격한 순서가 아닌 자연스러운 순환을 허용한다

### 게이트 (확인)

스펙 작성 준비도를 체크리스트로 판단한다.

게이트에 도달하면 [게이트 체크리스트](references/GATE-CHECKLIST.md)를 읽어 판정 기준, 출력 형식, 프롬프트 생성 형식을 참조한다.

**판정:**
- Must 항목이 모두 충족 → 스펙 작성 진입 가능
- Must 항목 미달 → 해당 항목만 짧게 추가 수집한다 (탐색으로 돌아감)
- Nice-to-have 미달 → 스펙 작성 중 보완 가능 (진입 허용)

**표현:** 미달 항목을 "불합격"처럼 보이게 하지 않는다. "이것만 확인하면 됩니다", "지금 진행해도 되고, 이것까지 보면 스펙이 더 단단해집니다"처럼 무엇을 하면 되는지와 선택권을 함께 보여주고, 아직 더 이야기해도 된다는 것을 알린다.

**게이트 통과 후 행동:**

게이트에서 스코프 분리가 필요하다고 판정된 경우, 먼저 **이번에 착수할 하나**(보통 첫 단계)와 **나머지(후속 단계 / 이번 목적 밖 항목)**를 구분한다.

- **이번에 착수할 하나**만 아래 선택지로 진행한다.
- **나머지 항목**은 backlog skill로 백로그에 등록한다. 공유 결정 추출과 순차 의존 기록은 [게이트 체크리스트](references/GATE-CHECKLIST.md) § 분리 항목 처리를 따른다.

분리가 필요 없으면(스코프 건전) 곧바로 아래 선택지로 진행한다.

사용자에게 다음 선택지를 제시한다:

1. **"스펙 작성"** — 현재 세션에서 스펙 워크플로우에 진입할 수 있으면 바로 진행한다(Feature/Bugfix 선택부터 시작). 세션 타입 제약 등으로 진입할 수 없으면, 작업 노트에서 붙여넣기용 프롬프트를 생성하고 새 스펙 세션에서 사용하도록 안내한다.
2. **"백로그 등록"** — 시기가 미정인 경우. backlog skill을 활성화하여 프롬프트 생성 형식과 동일한 내용으로 백로그에 항목을 추가한다. 등록 경로·형식은 `backlog-guide`가 정본이다.
3. **"보류·폐기"** — 논의 결과 지금 만들지 않는 것이 맞다고 판단된 경우. 사유를 사용자와 한두 문장으로 정리하고, 남길 곳(백로그 등)이 있으면 기록한다.

### 마무리

선택지 처리를 마친 뒤 "브레인스토밍을 마무리할까요, 더 이야기할 게 있나요?"라고 묻는다.

- **마무리**: 작업 노트를 삭제한다.
- **더 이야기**: 탐색으로 돌아간다. 새 생각을 꺼낼 마지막 기회로 자연스럽게 활용한다.

현재 세션에서 스펙 작성에 바로 진입한 경우, 노트가 스펙 작성의 입력이므로 마무리 질문은 requirements.md가 생성된 뒤에 한다.

## 에이전트 행동 규칙

- 이 워크플로우 중에는 스펙 문서(requirements.md, design.md, tasks.md)를 생성하지 않는다. 작업 노트는 스펙 문서가 아니다.
- 사용자의 아이디어에 무조건 동의하지 않는다. 기술적으로 더 나은 방향이 있다면 근거와 함께 제안한다.
- 질문 시 코드/DB/문서를 직접 확인할 수 있는 것은 먼저 확인하고 결과를 공유한다.
- 진행 단계를 사용자에게 명시적으로 알리지 않는다(자연스러운 대화 흐름 유지). 진행 판단은 작업 노트에서 도출한다.
- 게이트 확인 시에만 체크리스트 형태로 현황을 보여준다.
